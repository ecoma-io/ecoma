# Repository Instructions

## Source of truth

- Current code/config defines current behavior; inspect it before changing anything.
- `docs/architecture/*.md` describes the target design, not necessarily the current implementation. Do not implement planned state merely because it is documented.
- `docs/architecture/04-platform-facts.md` contains time-sensitive platform facts; verify current official provider documentation before relying on a platform limit or capability.

## Language

**English is the default for everything, with one closed list of exceptions: Vietnamese is used only for human-facing prose.**

Write **Vietnamese** in these human-facing prose surfaces, and nowhere else:

- Markdown documentation: `docs/` (see `docs/AGENTS.md` for its document rules), README files and `CONTRIBUTING.md` — every `.md` file except files named `AGENTS.md`.
- Code comments and JSDoc.
- Issue bodies and issue comments.
- Pull request bodies and review comments.

Write **English** for everything else, with no exceptions. Non-exhaustive list:

- Every file named `AGENTS.md` (agent instructions, in any directory).
- Identifiers: variables, functions, types, configuration keys.
- Test titles (`it` / `describe` / `test`), which describe behaviour rather than prose.
- Every string a program emits at runtime: console output, log lines, error messages, CLI output, spinner and help text — regardless of mechanism (`console.*`, a logger library, `process.stderr`, ...). Vietnamese without diacritics still counts as Vietnamese.
- The `message` fields of the Semgrep rules in `.github/semgrep/`.
- Commit messages, pull request titles, branch names.
- Database migration comments: `COMMENT ON` text in migrations is English, including when editing an existing comment. The product has not shipped, so rewriting a comment in place is allowed; a forward-fix migration is not needed for a comment-only change.

Additional rules:

- Keep proper nouns, technical and domain terminology, product and service names, framework and library names, protocol names, architecture patterns, and API names in English even when writing Vietnamese. Do not translate a term when translating it would reduce technical precision.
- Do not translate existing content just because this policy is new. Apply it when writing or editing.
- In an issue or pull request body written in Vietnamese, keep issue titles, branch names, pull request titles, file paths, and error codes unchanged.

## Language exemptions

The English rule applies to developer-authored content. The following are exempt and may be Vietnamese in any locale:

- **Product i18n content**: strings in locale files and registries (`apps/*/app/i18n/locales/*`, `vi:` content keys, locale display labels such as `Tiếng Việt`) are product data shown to the end user in their own locale, not developer-authored runtime strings.
- **Test fixtures and sample data**: test data that simulates user content — names, titles, sample bodies, example inputs — may be Vietnamese. This does not extend to test titles, assertions on developer-authored output, or any `Error`/`throw` a developer writes.
- **Human-facing repo metadata**: `.github/ISSUE_TEMPLATE` fields shown to a person (name/description of issue forms) are Vietnamese prose.
- **JSON `//` keys**: a `"//"` key is a comment (JSONC convention), so Vietnamese is valid in `//` keys of `nx.json`, `package.json`, `tsconfig*.json`, `wrangler.jsonc`.

## Communication

- Read and apply the documentation principles in [`docs/AGENTS.md`](docs/AGENTS.md) §2 whenever you write, materially revise, or review human-facing content: issue and PR bodies, review findings, reports, documentation, and technical explanations. Make that content easier to understand without changing its meaning: keep evidence, uncertainty, conditions, exceptions, limitations and exact identifiers intact, and never present an assumption as a verified fact. `.agents/skills/` is the source of truth; `.claude/skills/` and `.opencode/skills/` are generated by `pnpm dx repo-prepare`.
- Those principles override nothing: they sit below user instructions, these instructions, artifact templates and the language rules above. They are never a reason to pad content, add sections the task does not need, exceed the level of detail the task asks for, or force one structure onto every artifact.

## Non-negotiable architecture

- One service owns each database; another service must not access that database directly.
- Cross-service communication uses the defined API/event contracts, not shared database access.
- `llm-api` runs on Cloudflare Workers and serves under `/llm`.
- The database is quota authority and settlement authority; quota changes must remain reconstructible from durable database state.
- Inter-service events use the transactional outbox and idempotency.
- Secrets never enter Git, PR builds, or Preview runtime from production environments.
- One Cloudflare account owns every environment; secrets use native Worker Secrets and deployment environment mechanisms.
- Database changes use expand → compatible rollout → contract; prefer forward-fix over data rollback.
- Test placement, test category semantics and Nx test targets follow `docs/architecture/06-testing.md`; `test`, `test-integration` and `system-test` are the canonical target names.
- Do not introduce node-local application state that breaks recovery or topology changes.
- Observability must not become a serving-path dependency; never log prompt/response bodies.

## Change discipline

- Preserve existing behavior unless the task explicitly changes the contract.
- Inspect the affected Nx project/graph and repository configuration before editing.
- Make the smallest change that satisfies the task and run the relevant validation before finishing.
- Do not silently resolve documented not yet finalized, proposed or future-phase decisions into implementation.

## Workflow

**Canonical process lives in `docs/engineering/`; this section defines agent execution rules only.**

- [`docs/engineering/evolution-process.md`](docs/engineering/evolution-process.md) is the canonical lifecycle, Issue Type taxonomy and capability-state semantics. The five Issue Type values — Discovery, Modelling, Experiment, Delivery, Remediation — are carried by the native GitHub Issue Type (§4.1); recording them, including the current transition, is owned by `work-management.md` §2.3.
- [`docs/engineering/work-management.md`](docs/engineering/work-management.md) is the canonical GitHub work-management policy.
- [`docs/engineering/contribution-workflow.md`](docs/engineering/contribution-workflow.md) is the canonical procedure for carrying out work.
- [`CONTRIBUTING.md`](CONTRIBUTING.md) is the contributor entry point.

The five phases below are the **agent execution loop for one task** — Understand, Plan, Execute, Validate, Deliver. They are not the seven-step evolution lifecycle, and they do not replace it. Do not invent a third taxonomy: when a task needs lifecycle guidance, use `evolution-process.md`; when it needs Issue, Project, Milestone or PR semantics, use `work-management.md`.

- Priority: fix bugs first, then feature improvements — unless I ask to prioritise something specific; my call overrides these rules.
- Work follows five conditional phases — Understand, Plan, Execute, Validate, Deliver — skipped or combined as the task warrants.
- Before doing work, identify the product, its horizon (read from the Milestone commitment declarations per `work-management.md` §4.1), the Issue Type of the unit, the authoritative baseline, and any applicable Change Specifications (`evolution-process.md` §6.1, [`docs/changes/README.md`](docs/changes/README.md)).
- Never apply a future target to M1 work unless the task explicitly requires it; a Change Specification is design-ahead, never baseline.
- Never implement a proposal or an unaccepted decision as though it were accepted.
- For every material change — canonical baseline, accepted decision, committed Milestone scope, or shared contract — evaluate compatibility and impact ([`docs/changes/README.md`](docs/changes/README.md) §4).
- An M1 baseline change must trigger review of downstream dependent work (`docs/changes/README.md` §4).
- Root issues own outcomes and Project membership; sub-issues own work units and never join the Project (`work-management.md` §3).
- The orchestrator must detect conflicts between lanes and must never dispatch two agents to edit the same canonical file or contract without an integration plan.
- When a change affects a Change Specification, dispatch the change-impact workflow or ask its owner to revalidate (`docs/changes/README.md` §4).
- Target documentation and actual source code are different things: verify current behavior in source.
- Report a blocker only when a work item needs a classification or native GitHub capability that has no documented channel — a value outside the five Issue Types, or a capability with no interim path (`work-management.md` §2.3). While that interim channel exists (org not configured yet), use it instead of blocking; do not invent substitute classification.
- Every independently trackable unit of implementation work needs a GitHub Issue: search existing Issues and PRs first, and reuse a suitable Issue or create one if none exists. Criteria and the ledger/precondition/experiment distinction → `work-management.md` §2.
- Well-defined implementation work: identify or create the Issue, then create a branch and open a linked draft PR against the default branch before editing code. Exploratory work with unclear scope: investigate enough to define the work first, then create the Issue and start implementing.
- No new Issue for standalone explanations, advice, or reviews contained within an existing PR; track independent follow-up work separately.
- Close an Issue as completed only when the outcome is achieved, evidence exists, and reconciliation is recorded; `not planned` and `duplicate` are the documented exceptions — see `work-management.md` §2.6. `Closes #N` means the PR completes the whole Issue; use `Refs #N` otherwise.
- Every commit — mine or a subagent's — is cryptographically signed; never push an unsigned commit. If commit signing isn't available, tell me instead of working around it.
- When a task decomposes into independent units, dispatch them as concurrent subagents (multiple Agent calls in a single message) instead of implementing units one at a time. Put the issue number, branch, and draft PR in each subagent's prompt; give agents that edit the same repo concurrently their own worktree (`isolation: "worktree"`); and dispatch a dependent unit only after the units it depends on have reported back. The coordinating session synthesizes results and routes follow-ups; it does not do the units' file edits itself unless explicitly asked.
- Each dispatched subagent gets an explicit scope lock — the files or projects it may change — and must stay inside it, must sign its commits, and must report back rather than widen scope. The coordinating session owns shared files and integration, and verifies every subagent's commits are signed before pushing.
- Single-unit work with nothing to parallelize can be done directly. Requests phrased as handoff/handover are full ownership transfers to a single subagent that carries the unit end to end — no parallel split, no supervision. Report every dispatched subagent in the session summary alongside issues filed.
- Validate on the real artifacts: run the relevant checks locally before committing; after pushing, monitor CI and Code Review/Scanning and resolve every problem until CI is green and all review conversations are resolved. Finish by reporting verified results or blockers and updating the Issue and PR to match reality.

### Skills

- `.agents/` is the canonical source for both skills and subagent definitions. `pnpm dx repo-prepare` generates `.claude/skills/`, `.opencode/skills/`, `.claude/agents/` and `.opencode/agents/` from it; never author generated files directly.
- Agent definitions live in `.agents/agents/<name>.md`. The frontmatter is Claude's shape (`name`, `description`, optional `tools`, `model` and `mode`); `mode` accepts exactly `primary`, `subagent` or `all`, and the generator emits `mode: subagent` when the source omits it. `pnpm dx sync-agent-config` derives the OpenCode variant, which declares `mode` and converts `tools` into `permissions`; `mode` is never emitted into the Claude variant. Definitions carry no `model` value until the repository has a model-selection policy — leave model choice to the runtime.

#### Agent catalog

| Agent                      | Responsibility                                                                                                                                                                   | Boundary                                                                                                |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `engineering-orchestrator` | Classifies work by Issue Type and multi-horizon context, reads GitHub state, selects skills, decomposes into units, dispatches specialists, integrates and owns final validation | Primary; no `Edit`/`Write`, must not edit product code; `Bash` is granted, so this is instruction-level |
| `repository-analyst`       | Explores code, configuration, contracts and docs; reports facts with references, blast radius and unknowns                                                                       | Read-only enforced by the tool set: no write tool and no shell                                          |
| `architect`                | Reviews boundaries, dependency direction, invariants, ADRs and trade-offs; detects overengineering                                                                               | Read-only enforced by the tool set: no write tool and no shell                                          |
| `implementer`              | Executes one delivery slice inside an explicit scope lock, writes and runs tests, reports gaps                                                                                   | Writes with `Edit`/`Write`/`Bash`; the scope lock is instruction-level                                  |
| `verifier`                 | Adversarially re-derives claims and runs the matching validation target                                                                                                          | No `Edit`/`Write`; `Bash` is granted for validation and must not be used to edit — instruction-level    |

- Delegation contract: only `engineering-orchestrator` dispatches. Each dispatched agent receives an explicit scope lock and never inherits a wider one. Agents that edit the same repository concurrently get separate worktrees where the harness provides them. The orchestrator integrates results and owns final validation. Tool-level enforcement is limited to withholding a tool entirely: an agent without any write tool and without `Bash` cannot modify the repository, but a granted `Bash` can write files regardless of the missing `Edit`/`Write` tool, and no granted tool is path-scoped. Every scope lock and every "read-only" role that holds `Bash` is therefore instruction-level.
- `CLAUDE.md` is not generated. Claude Code reads `AGENTS.md` as project instructions when no `CLAUDE.md` is present, so `AGENTS.md` is the only source of agent instructions.
- Use a skill when the request matches its `description` trigger. Read only the skills relevant to the current task — do not load every skill.
- Canonical documentation and these repository instructions outrank every skill. A skill never redefines policy, never widens the permission this file grants, and never overrides a template or language rule.
- If a skill contradicts a canonical document, follow the canonical document and report the conflict instead of silently choosing one.
- `github-issue` governs Issue authoring; `commit-message` governs commit messages; [`docs/AGENTS.md`](docs/AGENTS.md) §2 governs human-facing prose. Task skills for lifecycle steps (`engineering-understanding`, `engineering-discovery`, `domain-modelling`, `architecture-evolution`, `feature-modelling`, `delivery-slice`, `verification`, `reconciliation`) govern how to execute that step, not what the policy is; `change-impact` (`.agents/skills/change-impact/SKILL.md`) governs impact assessment on dependent Change Specifications after a material change (`docs/changes/README.md` §4).

### Stop and report

Stop and report back — do not guess, widen scope, or improvise a workaround — when:

- A decision needed to proceed safely is missing or has not been accepted.
- Canonical artifacts contradict each other and no authoritative source resolves it.
- The real scope exceeds the Issue or PR you were given.
- Verification cannot be performed, or the available evidence is too weak to support a claim.
- The change risks breaking an invariant, a security boundary, or backward compatibility.
- Commit signing, required tooling, or a required credential is unavailable.

### Pull requests

- One PR = one independently reviewable logical change; judging that stays a human/AI review responsibility — no check approximates it from file or project counts, and `pr-check` does not inspect the diff. A PR that is neither a feature nor a bug fix (docs, chore, CI, refactor...) is legitimate and uses the `others` template, and a single logical change may still touch several Nx projects, tests, docs and configuration files. Development branches may carry any number of commits — the repository never requires one commit per PR.
- PR linking and closure rules → `docs/engineering/work-management.md` §5. `Closes #N` only when the PR completes the whole Issue; not every PR needs an Issue.
- `pnpm dx pr-check` is the machine-enforced PR policy entry point; CI runs it on every PR:
  - PR title: any valid Conventional Commit type (`feat`, `fix`, `chore`, `docs`, `refactor`, `ci`, ...). Scope is optional; when present it must be exactly one valid Nx project, e.g. `fix(dx): ...`. Squash merge makes that title the commit subject and the branch's commit messages the commit body — the repository settings are set so the PR body is not included — and the title drives changelog generation, so both are written deliberately.
  - Development commits: any number are allowed, of any Conventional Commit type (`feat`, `fix`, `chore`, `docs`, `refactor`, `ci`, ...); no type-count invariant is enforced.
- Squash merge only: merge commits and rebase merges are disabled, direct merges and direct pushes to `main` are prohibited, and every PR lands through the merge queue — these are GitHub repository/ruleset settings, which `pr-check` deliberately does not pretend to enforce.
- Feed the queue proactively: the moment a PR is approved, its CI is green, and nothing blocks it (no unmerged PR it depends on — stacked children retarget and follow once their base lands), put it into the merge queue immediately; a green PR never sits idle to be batched with others.
- Interdependent work uses GitHub Stacked PRs; keep rebasing the downstream branches so every child stays in sync with the PR it depends on. Rebase onto the latest default branch before pushing and before marking a PR ready for review.

## Local Development Preview

- Before operating the local stack, read `docs/architecture/local-development/03-operations.md`.
- Deploy or refresh the preview with `pnpm nx run-many -t local-up -c local` (Nx coordinates ordering; each deploy project runs its own colocated entry).
- Wait for the command to finish successfully; do not claim the stack is ready merely because the deployment command started or a container exists.
- Confirm the stack end to end with `pnpm nx run platform-deploy:local-smoke -c local`; read the resulting URL from `.env` (`ROOT_HOST=fbi.com:<port>`) — never guess the dynamic port or construct a URL from assumptions.
- Report the resulting preview URL clearly to the user.
- If deployment fails, report the actual failed step and the actionable error; do not silently substitute manual Docker/Pulumi commands or a different serving method.
- Tear down with `pnpm nx run-many -t local-down -c local` (no global teardown order; platform deletes its PostgreSQL volume on every down — local data is not preserved).
- Distinguish successful HTTPS smoke-test verification from whether the developer's browser trusts the local self-signed certificate.
- Never expose credentials when reporting status or URLs.
- After deleting a worktree that had a local deployment, clean up its Docker resources with `pnpm dx local-cleanup` (use `--dry-run` first to preview). Cleanup deletes managed resources including persistent PostgreSQL volumes, but only for worktrees confirmed absent — ownership checks are mandatory and neither cleanup path can touch unrelated Docker volumes.
