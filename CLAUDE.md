# Agent Guidance

## Ecoma

Ecoma is a self-hostable, "fair-code" labor operating system where humans, AI, and rules/code function as the same type of labor resource (Role/Filler); workflows—encompassing both deterministic processes and reasoning tasks—are co-designed by humans and AI directly within the engine; every output passes through a checkpoint with confidence levels adjusted based on each tenant's data; and human attention is treated as a resource to be measured and optimized.

## Working Principles

Prioritize correctness, clarity, and evidence over speed; bias toward caution on non-trivial work, use judgment on trivial tasks. These rules apply to every task unless explicitly overridden, and the numbering is stable — other docs cite "Rule N" (notably Rule 13, machine-enforced on both halves: the _version-marker_ subset in comments/test titles by `local/no-journey-markers` + `dev-cli check-journey-markers`, and the _durable-name_ half — no `v2`/`phase-3`/`wip` in symbol, file, or target names — by `local/no-journey-marker-names` for exported identifiers plus the same dev-cli command for file/directory and Nx target names; only the residue the pattern cannot judge — non-exported locals, config keys beyond targets — stays on review).

- **Rule 1 — Think Before Coding** — State assumptions before acting; ask when uncertain rather than guess; offer multiple readings when ambiguous; challenge needless complexity.
- **Rule 2 — Simplicity First** — Before writing code, walk the ladder and stop at the first rung that meets the requirement: (1) no code — drop the need, or use config / existing behavior; (2) reuse code already in the repo; (3) the language stdlib or an already-installed dependency; (4) only then new bespoke code. Small because it's necessary, not golfed — never cut validation, error handling, security, or accessibility to shrink a change.
- **Rule 3 — Surgical Changes** — Don't refactor or polish stable/unrelated code while making a surgical change; report unrelated dead code you find, don't auto-remove it.
- **Rule 4 — Goal-Driven Execution** — Define verifiable success criteria up front and iterate until they're met; don't follow steps that no longer serve the goal.
- **Rule 5 — Use the Model Only for Judgment Calls** — Model for classification, drafting, summarization, extraction, tradeoffs; code for routing, retries, deterministic transforms, parsing, validation, repeatable checks. If deterministic code can answer or validate it, use code.
- **Rule 6 — Surface Conflicts, Do Not Average Them** — When patterns conflict, pick one (prefer the newer/better-tested), explain the choice, and flag the loser for cleanup.
- **Rule 7 — Read Before You Write** — Inspect context, exports, immediate callers, and shared utilities before changing code (mechanics in Tool Hygiene below).
- **Rule 8 — Tests Verify Intent, Not Just Behavior** — Tests encode why behavior matters; a test is inadequate if the important logic can change without failing it.
- **Rule 9 — Checkpoint After Every Significant Step** — Summarize what's done, what's verified, and what remains; if lost, stop and restate status before continuing.
- **Rule 10 — Match Codebase Conventions, Even If You Disagree** — Prefer repo conventions over personal preference; raise a harmful one explicitly instead of silently diverging.
- **Rule 11 — Fail Loud** — Never mark work complete if anything was silently skipped; never claim tests pass if any were skipped or failed; expose uncertainty rather than hide it.
- **Rule 12 — Default to Concise, and Readable on the First Pass** — Lead with the conclusion/change, then the reason; compress prose but never technical tokens (code, paths, API names, commands, errors stay exact); don't narrate tool calls. Suspend brevity for security warnings, irreversible-action confirmations, and multi-step sequences. Governs prose only — never suppresses assumptions (Rule 1), checkpoints (Rule 9), or loud failure reporting (Rule 11). **Short is not the same as clear, and compressing can cost more than it saves.** One idea per sentence. A caveat gets its own sentence instead of being nested as a clause — three true qualifications stacked into one sentence make the reader parse a tree rather than read a line. State the answer before reframing the question; a reframe first makes the reader hold your framing in their head before they get anything back. Prefer the plain sentence over the compressed one: an aphorism is short, but it packs the reasoning inside itself and leaves the reader to unpack it.
- **Rule 13 — Name for the End State, Not the Journey** — Durable names must describe what a thing _is_, never the transient process that produced it. Keep phase/milestone/sprint codes, dates, ticket IDs, and relative qualifiers ("new", "old", "v2", "phase-3", "step-1", "temp", "wip") out of anything that outlives the task: symbol/file/package names, command and target names, config keys, and **test case titles**. A test is titled by the behavior it pins, not the phase it was added in. When a temporal label feels necessary, that signals the work belongs in a commit message, plan, or PR description — not in the code's vocabulary.
- **Rule 14 — Derive, Then Configure, Only Then Hardcode** — Before a literal value lands in logic, climb the same ladder as Rule 2, applied to _values_ instead of code: (1) derive it from an existing source of truth at read time — scan the tree, read git state, parse a schema — so it can never drift and nothing needs manual syncing; (2) when there is no source to derive from, author it once as a single named config (a JSON file, one exported constant) that every consumer imports rather than redeclares; (3) only when both are infeasible, hardcode it inline, with a comment naming which rubric criterion justified skipping rungs 1–2. A hardcode passes the rubric only if all three hold: it is intrinsic to a fixed external contract (a protocol constant, a file-format field) rather than a workspace decision that could change; deriving or centralizing it would need infrastructure disproportionate to its one use; and it appears in exactly one place — a value copied across ≥2 files was never a valid hardcode, it was an unsynced config that skipped rung 2. Treat a hardcode that fails any criterion as a bug waiting for the next rename, not a style nit — flag it in review the same as an uncovered invariant.

## Tool Hygiene

Deterministic rules that prevent the most common wasted tool round-trips (each failure burns tokens and a retry):

- Subagents that create or modify a file must Read it first unless they are the ones creating it new (the Edit/Write tools already enforce read-before-write for the main agent).
- If an Edit fails with "modified since read", re-read the file immediately before retrying — a formatter or linter changed it.
- Do not pass `pages` to Read unless the target is a PDF; an empty or non-PDF `pages` value is rejected.
- Prefer the Grep and Glob tools for code search when they are available; if they aren't in the current tool set, fall back to `rg` or Bash `find`. Don't Read a directory path — list it with Glob (or `find`).
- Confirm a path exists (Glob, or `find`/`ls` via Bash) before Read when you are inferring the path rather than copying it from prior output.
- Bash cwd already persists at the repo root — do not prepend `cd <repo-root>` to commands; use repo-relative or absolute paths directly. Env vars and shell state also do not persist between calls, so re-export them inline only in the same command that needs them.

## Workspace Execution

Defaults Claude Code would reach for that are wrong here — override them:

- **`pnpm nx` is the only task runner.** Build/test/lint/serve/run targets through `pnpm nx` — never `npm`, `npx`, `yarn`, or global `nx`, and never call a language toolchain directly when an Nx target exists. Each project declares its `build`/`test`/`lint`/etc. targets and tags explicitly in its own `project.json` (shared `cache`/`inputs`/`dependsOn` config is hoisted to `nx.json` `targetDefaults`), so `project.json` plus `nx.json` `targetDefaults` are the source of truth — read them before assuming a target exists.
- **Polyglot projects (Go/Rust/Python) follow the same contract.** Their `project.json` targets are hand-written `nx:run-commands` over the language's own toolchain (`go`/`golangci-lint`, `cargo`, `uv`/`ruff`) — never inferred. What IS inferred are the cross-project edges: the local `nx-polyglot-graph` plugin (`nx.json → plugins`) reads manifests statically so `nx affected` sees Go/Rust/Python dependencies. Scaffold with `dev-cli scaffold-lib --lang <ts|go|rust|python>`; the definition of done above applies unchanged.
- **Definition of done for a code change:** `pnpm nx affected -t lint test typecheck build e2e` passes (Rule 4, Rule 11) — the same five targets CI gates, so a shorter local run just moves the red to the PR. `typecheck` is a first-class gate: the Vite/esbuild `build` targets strip types without checking them. `e2e` is one too: it builds the app and drives it in a real browser, which is the only place a runtime-only regression can surface. Details: `CONTRIBUTING.md`.
- **Commits** follow Conventional Commits (commitlint-enforced). Details: `CONTRIBUTING.md`.
- **Release is app-centric; the releasable unit is a shell that emits a distributable artifact, never a lib.** An app earns a version when it has a `package` target producing something an operator installs and can name. No app in the workspace has one today, so `nx.json` carries no `release` configuration — it returns together with the first app that earns a `package` target. **Libs are internal-only** — `private: true`, buildless, `main → src/index.ts`, bundled into each consumer via `tsconfig.base.json` paths; third-party deps live in the **root** `package.json` (single-package monorepo, no per-lib dep declaration — `@nx/dependency-checks` is deliberately off). Publishing a lib to npm stays a reserved seam (it would force a workspace + build step + a real `main`).
- **Don't launch long-running runtime targets as a side effect.** `serve` targets (the Storybook dev server) exist for runtime proof — start them only when the task needs runtime evidence, and stop them when done; don't start them just to "check something".

## Development Workflow

How work moves from request to done here. These encode corrections the user has given repeatedly — treat them as defaults, not suggestions.

- **Evidence over assertion.** Never declare something works, exists, or is spec-compliant from memory. Prove it: read the installed dist / current library docs (not training memory) for any API; exercise _every_ mode/branch a change touches before calling it done (a feature "verified" in one mode with a bug in the other is a Fail-Loud violation, Rule 11). When correcting a fact, re-verify the replacement at the source first — do not swap one wrong fact for another.
- **Scaffold openly; never fake done.** A skeleton, interface, or unimplemented seam is legitimate when its incompleteness is _loud_ — it throws or `TODO`s, or its test is a visible `.todo` (never a committed `.skip`/`.only` — the `local/no-focused-or-skipped-tests` lint rule blocks those) — and you state the status plainly; designing the shape before filling it is good engineering. What's banned is the _disguise_: a placeholder that returns a fake value to turn a check green, calling something "done" or "works" without exercising the real user-facing path, or weakening a test to pass (Rule 11, Rule 8). The tell — run the real path: it works, or it fails loudly; it never silently pretends. The line is honesty-of-status, not whether unfinished code exists.
- **The three test tiers are the same in every language; only the mechanism differs.** A **unit** test isolates the unit under test from every project-internal collaborator. An **integration** test uses real collaborators, and is justified only when that interaction _is_ the behavior being pinned — "the unit test was annoying to isolate" never is. **e2e** tests drive built apps, may span several, and live only in an `<app>-e2e` Nx project (`type:e2e`), never co-located — `Foo.e2e.test.ts` / `foo_e2e_test.go` / `foo_e2e_test.py`, a placement `check-project-conventions` rejects anywhere else. Mock project-internal collaborators, never pure third-party libraries. Tier is carried by the filename suffix, co-located with the code — except in Rust, where the toolchain already carries it better:
  - **TS** — `Foo.test.ts` (unit) `vi.mock`s every project-internal collaborator (relative or `@ecoma-io/*`), enforced by `local/no-unmocked-internal-imports`; `Foo.integration.test.ts` may use real ones. `vitest run` runs both; e2e is Playwright.
  - **Go** — `foo_test.go` / `foo_integration_test.go`, both in the package under test. `go test ./...` runs both; no build tags — a second tier mechanism would only drift from the name it duplicates.
  - **Rust** — the tiers are Cargo's, not ours. Unit is `#[cfg(test)] mod tests` **inside** the file (it can reach private items); integration is `tests/*.rs`, which Cargo compiles as a separate crate that sees only the public API — a compile-time boundary, stronger than any lint could be. `cargo test` runs both.
  - **Python** — `foo_test.py` / `foo_integration_test.py`, co-located inside `src/<module>/`. `uv run pytest` collects both.
  - Only TS's unit tier has its isolation machine-enforced, and only Rust's is compiler-guaranteed; **Go and Python rely on review**, so a "unit" test there that quietly reaches a real collaborator is a Rule 11 miss, not a shortcut.
- **Resolve conflicts upstream-first.** When sources of truth disagree, fix the upstream one first; never patch a downstream copy before the upstream truth is settled.
- **A fix covers its invariant, not just the reported site.** Every fix establishes some rule — "this glyph declares its stroke", "a connector name is unique", "autostart actually works". Before writing code, state that invariant and enumerate _every_ place it must hold; then cover them all in one pass, or name each deliberate exclusion in the PR body with its reason. The recurring failure is not a wrong fix, it is a fix scoped to the symptom that leaves the invariant half-true: an attribute applied to seven call sites but pinned by tests at six; a uniqueness key changed in the store while resolution and seeding still compare a different way; a capability made real while the state that reports it stays a proxy. Each of those _looks_ finished, ships, and comes back as a new defect. This is where Rule 3 stops: surgical means "don't refactor unrelated code", never "fix only the line that was reported" — a half-covered invariant is a new bug, not a follow-up. **A reviewer who finds an uncovered site treats it as blocking**; filing it as a fresh issue converts your own incompleteness into someone else's debt.
- **Additive before destructive.** Upgrade/add first, verify green, then remove. Never delete or overwrite before the replacement is proven.
- **Extend before you create.** Put new content into the existing structure (section, doc, invariant, job model) unless it genuinely cannot fit. Defaulting to a new section/file/abstraction when one already exists is the single most-corrected habit in this repo (Rule 2, Rule 3). Keep one source of truth: delete a duplicate rather than sync two.
- **Mirror the user's language in user-facing prose.** This project works in Vietnamese: final reports and explanations to the user default to Vietnamese. Code, identifiers, comments, commit messages, and technical tokens stay English.
- **No journey markers in shipped code or durable names.** Roadmap/version tags (`0.4`, "arrives in 0.2") never render in the product or land in comments/test titles, and journey tokens (`v2`, `wip`, a trailing `-new`/`-old`/`-temp`, phase/sprint ordinals, dates, ticket IDs) never land in exported identifiers, file/directory names, or Nx target names — enforced by the `local/no-journey-markers` and `local/no-journey-marker-names` ESLint rules (`shared/tools/eslint-local-rules`) plus the `dev-cli check-journey-markers` command (`shared/tools/dev-cli`) for non-JS/TS/Vue file contents and for names, all reading the single pattern source `journey-markers.config.json` at the repo root (Rule 13). Add a _user-facing surface_ only once it has real function — reserve the architectural _seam_ (model · manifest · routing) in the design rather than rendering a dead one (distinct from the honest internal scaffolding allowed above).

## Agent & Model Routing

When delegating to a subagent, pick the cheapest tier that fits the work. Task difficulty is a judgment call, not a keyword match — decide per task.

- Read-only / search / explore (sweep many files, locate code, audit, list, trace usages) → use the `Explore` agent. It runs a cheap model by default; do not hand-set `model`.
- Deterministic, repeatable mechanical work (transforms, parsing, validation, formatting, derive-from-source) → not a model task at all (Rule 5); use a script or command.
- Mechanical work that still needs natural-language judgment but whose reasoning is FULLY pre-baked — the prompt hands over an explicit decision procedure AND a machine-readable pass/fail rule set, so the agent executes rather than strategizes → `model: "haiku"`. The test is on the work, not a keyword: if the agent would have to derive the strategy, choose the approach, or judge fuzzy criteria itself, its reasoning is NOT pre-baked — that's `sonnet`, not haiku. (This heuristic is a judgment call about where the reasoning lives, not an empirically fixed Opus/Haiku boundary; when unsure, size up to sonnet — a too-weak tier costs a wrong answer plus a retry.)
- Bounded implementation with clear scope and verifiable success criteria (scaffold per an established pattern, apply a defined refactor, run a target and report) → spawn an agent with `model: "sonnet"`.
- Ambiguous, architectural, cross-cutting, or hard-reasoning work → default tier (Opus); no override needed.

Effort (reasoning depth) is a separate axis from model (which brain). Set it independently — a cheap model can run high effort, a strong model can run low effort — and pick the lowest effort that reliably gets it right. When unsure, omit `effort` so the agent inherits the session effort; only override when you're confident the work needs more or less than the default.

- Mechanical, single-step, or low-branching work (apply a defined edit, run a target and report, restate facts) → `effort: "low"`.
- Routine implementation with a clear path and few unknowns → `effort: "medium"`.
- Multi-constraint reasoning, design tradeoffs, debugging with unclear cause, or adversarial verify/judge stages → `effort: "high"` and up (`xhigh`/`max` only for the hardest, highest-stakes calls where a wrong answer is expensive).

Don't raise effort to compensate for a too-weak model, and don't raise the model tier to compensate for too-low effort — diagnose which axis is actually short and adjust that one.

The session (main-loop) effort is user-controlled via `/effort` — it is not a setting you can raise on yourself mid-session. When a task clearly exceeds the current session effort, say so and recommend the user bump `/effort` (Rule 11), rather than silently proceeding at too low a level.

Do not add hooks that guess task difficulty (model or effort) from prompt keywords — the cost of misrouting upward (a hard task on a weak model, or trivial work burning max effort) is a worse answer plus a retry, which no regex can prevent.

## Documentation

The workspace is organized domain-first. A **subsystem** is any top-level directory holding tracked files: a product domain (owning its own `apps/` and/or `libs/`) or the cross-product `shared/` (`shared/libs`, `shared/tools`, and `shared/apps` — workspace-owned app shells serving shared infrastructure rather than any one product) are both subsystems, and so — as a special case with no parent directory to name it — is the repo root itself. `dev-cli check-subsystem-readmes` derives the subsystem list straight from the tree (`deriveSubsystemRoots`), so a subsystem that is deleted drops out of every gate on its own; nothing to update by hand. Directory-scoped mechanics live in nested `CLAUDE.md` files loaded on demand — e.g. `shared/libs/core-ui/CLAUDE.md` (primitive artifact pairing, token source of truth). A subsystem carries its own `CLAUDE.md` for architecture and rules specific to it; the layout exists so those rules load automatically when working inside it. Root CLAUDE.md holds workspace-wide principles, conventions, and routing; put per-directory mechanics in the nested file, not here. Human-facing setup and contribution steps live in `CONTRIBUTING.md`.

**Every Nx subproject (each `project.json`) carries a `CLAUDE.md`** — it is the only channel that reliably puts a subproject's invariants in context _before_ code gets edited (inline comments only help after the right file is opened). Scaffolding a new project includes writing it. Existence is enforced by `dev-cli check-claude-md` in CI; content quality is not mechanically checkable and stays on review. The mandate comes with anti-boilerplate constraints, in the shape the existing files demonstrate:

- Open with the scope line ("Directory-scoped mechanics only — principles live in the root `CLAUDE.md`") plus the Nx project name, import alias (if importable), and tags.
- Content is only what reading the code does _not_ reveal: invariants, footguns, pairing rules, run mechanics. Point to the owning tier for anything covered there (root, `shared/`, product root) — never copy it down (one source of truth).
- Length is proportional to real content: a thin shell gets a short boundary card stating its role and where its rules live; padding to look thorough is itself a violation.

**Every Nx subproject also carries a `README.md`**, mandatory the same way as `CLAUDE.md` above, with existence and structure gated by a new `dev-cli check-subproject-readmes` command. Every subsystem root's `README.md` gets the same treatment, extending the existing `dev-cli check-subsystem-readmes` frontmatter gate. Both kinds — subsystem-root and subproject — must exist in exactly 3 language variants (`README.md` in English as the canonical/default file, `README.vi.md`, `README.zh.md`), sharing one frontmatter format per kind (`name`/`lang`/`description` for a subsystem root; `name`/`subsystem`/`lang`/`description` for a subproject) and cross-referencing each other by filename convention. **The repo root's own README is the one exception: it carries no frontmatter at all** — it has no parent directory to name it and no area vocabulary to feed, so `check-subsystem-readmes` holds it to a lighter bar than every other subsystem: the 3 variants must exist and each must open with the shared language-switcher nav line pointing at its two siblings. The 3 language variants of any README must stay in semantic agreement: facts, instructions, and links must not diverge across languages, though wording may. Its machine-decidable half is gated: both README commands require every variant to name the same **technical tokens** — the inline code spans, compared in rendered form, so a name wrapped across two source lines counts as the different name it renders as. Rule 12 already draws that line ("compress prose but never technical tokens"), which is what makes the check deterministic rather than a judgment call. Whether the prose _around_ those tokens means the same thing still is a judgment call, so it stays advisory via `repo-care` rather than blocking a merge.
