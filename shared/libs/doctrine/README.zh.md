# doctrine

<!-- readme:why -->

## 为什么需要它

ecoma 的设计先在文档里定下来,然后才在代码里定下来:各个 North Star、每项机制
必须满足的规格、部署章程,以及评审所依据的量表。这些文档是对外公开的,所以它们
需要一个与其所约束的代码同步版本化的归处,而不是散落在旁边的某个文件夹里。

给它们一个独立的 project——而不是把 Markdown 直接丢进渲染它们的站点——换来一件
真正重要的事:这棵树变成了工作区可以检查的东西。一份存在却触达不到读者的文档,
正是文档站点失败的典型方式,而且它是**静默**失败的,因为没有人会报告一个自己压
根不知道存在的页面。这里的逻辑选择拒绝这种形态,而不是绕开它继续渲染。

<!-- readme:consumers -->

## 谁在使用它

只有 `shared/apps/doctrine-site`。它读取目录树,把文档清单交到这里,再渲染返回
的结果。

由于这个 project 是真实的 Nx 节点、并且站点确实 import 了它,修改一份文档就成
了 `nx affected` 能看见的变更——这也正是内容为什么放在库里,而不是放在展示它的
应用内部。

<!-- readme:ecosystem -->

## 它处在什么位置

放在 `shared/`,因为顶层文档覆盖每一个产品领域——platform、RPA 和 Hub 都在
内——而 `shared/` 正是工作区存放不专属于任何单一产品之物的地方。

模块本身是纯的:它接收一份文档清单、返回排好序的分节,从不触碰文件系统。读取目
录树是调用方的职责,而这恰恰让这里的每一条规则都无需磁盘上的样例目录即可测试。

<!-- readme:boundary -->

## 它刻意不做的事

- **不访问文件系统。** 调用方负责读取,这里负责判定。
- **不内置分节顺序。** 顺序通过参数传入,并与目录树做**双向**校验。在这里写死
  一个默认值,等于对本 project 看不见的内容做出断言。
- **没有标题映射表。** 标题取自每份文档自己的标题行,因此改标题即改导航条目,
  不存在第二处需要同步修改的地方。
- **不为译本另立条目。** `role.vi.md` 就是另一种语言的 `role.md`,因此它挂在被
  它翻译的那份文档上,绝不单独成为导航条目——三份都列出来,读者就会看到同一份
  规范三次。
- **不负责渲染。** 主题、路由与搜索属于站点。
