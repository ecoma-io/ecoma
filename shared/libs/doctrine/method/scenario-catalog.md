# Scenario catalog

The regression asset of the corpus. Each row is a scenario the design must
answer, with the verdict it currently carries. A verdict naming a patch is the
useful kind: it records that the scenario **found** something and where the
answer now lives, so a later change to that section can be checked against the
case that forced it.

Scenario ids are stable and are cited from other documents. They are never
renumbered and never reused.

## Open blind spots

Each of these is a crossing between two mechanisms that no scenario has yet
driven. They are listed rather than resolved, because a blind spot named is a
scenario waiting to be written, while a blind spot resolved in the abstract is a
guess.

- A sub-actor failing repeatedly while calibration binds to the filler — is the
  cause visible?
- Tenant purge against the lockfile and entitlement of an already-purchased
  block.
- A suspended tenant while a node holds an unfinished session.
- Release tagging when the private trunk and the public tree fall out of step.
- An attended UI offline holding a claimed Action Item, when the lease TTL
  expires while the machine has no network.
- A block's `migrations[].down` against a running instance pinned to the old
  digest.

Two entries that stood here have been **closed against existing text** rather
than left as open blind spots, because each was already answered and a
standing-but-answered blind spot is the M3 staleness the method warns against:

- _A test run scope against a time-travel query_ — answered in Working Data §1:
  "neither does a time-travel read as of a log position on a production table"
  see a test run's writes (the S63 patch).
- _`environment: test` against a Role's filler pool_ — answered in Role §3 as an
  engine law: a filler with `environment: test` "is not eligible for a production
  task, whatever its tier."
