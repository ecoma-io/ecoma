# Block

## 1. Definition

A Block is **a typed manifest bundling a set of ecoma entities with default
values and dependencies**, distributed through the Hub.

> **A template is a Block curated for a vertical.** The "template" level of the
> default cascade (Composition §3) is **the set of Blocks a tenant has
> installed**, resolved in a priority order the tenant declares. From here on,
> "template" has a mechanical definition rather than being a word that means
> whatever the reader assumed.

## 2. The manifest

| Field          | Content                                                                                                                                                                                                                                               | Required                           |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| `identity`     | namespace/name plus semver; the digest is generated by the registry and is content-addressed                                                                                                                                                          | ✅                                 |
| `publisher`    | A signing identity (sigstore)                                                                                                                                                                                                                         | ✅                                 |
| `contents`     | A list of **typed** entities: process-definition, contract, criterion, role, macro, script, app-profile, driver, cascade-defaults, table-definition, metric-definition — an open taxonomy                                                             | ✅                                 |
| `defaults`     | The cascade values this block contributes at the template level                                                                                                                                                                                       | ⬜                                 |
| `dependencies` | Other `block@range`                                                                                                                                                                                                                                   | ⬜                                 |
| `scope`        | **A mandatory summary of capability**: does it hold irreversible effects? which credential handles? which domains? what spawn policy? the highest classification of knowledge it carries? This is the source of the scope disclosure shown at install | ✅                                 |
| `license`      | Apache/CC0 for free blocks, or a publisher EULA for paid ones                                                                                                                                                                                         | ✅                                 |
| `migrations`   | The migrations an upgrade to this digest must run. **Each declares either a `down` path or `irreversible_upgrade: true`** — declaring neither is read as having no way back, conservatively, exactly as North Star §8 requires                        | ✅ where an upgrade has migrations |
| `attestations` | Signature, the analysis result from packing, and the verified badge where one exists                                                                                                                                                                  | ✅ automatic                       |

## 3. Two trust classes of artifact

| Class          | Contains                                                                                                                                                                                       | Checkable by                                         | Default install policy                                                                             |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| **Definition** | Processes, contracts, criteria, roles, macros, app profiles, defaults                                                                                                                          | **Complete** static analysis                         | Installable after disclosure                                                                       |
| **Code**       | Drivers, custom rule fillers. **A connector API is exactly a rule filler plus a Contract, distributed here** — this is ecoma's answer to an integration library, needing no concept of its own | Signature and sandbox; it cannot be analysed through | **Rejected where the publisher is not verified**; always requires an explicit administrator opt-in |

## 4. Identity, version, lineage

Semver is for people; **the digest is for machines**. An install pins the digest
into the tenant's **lockfile**. The lockfile is a versioned artifact, so a tenant
wanting governance runs lockfile approval as an ecoma workflow.

**There is no diamond problem at runtime.** Every entity pins its own version, so
two blocks carrying two different Contract versions coexist. Conflict survives
only at the index resolution layer, where it can be reported rather than
silently resolved.

A tenant forking a block creates a new version with **lineage** back to the
original; merging upstream is a pair-design task. Every materialised entity
carries provenance pointing at `block@digest`.

## 5. The publish lifecycle

```
git repo (development, fork, PR)
  → pack: schema check plus FULL static analysis (Composition §4)
  → publisher signature → push to OCI → transparency log → index
  → (optional) verified review, itself an ecoma workflow → attestation
```

## 6. Install — six steps, reusing mechanisms that already exist

1. `resolve` name@range to a digest; `verify` the signature and the transparency
   log.
2. **Re-run static analysis on the tenant side.** The publisher's claim is not
   trusted — the analysis is cheap and the asymmetry of being wrong is not.
3. **Scope disclosure** before installing. Where the analysis finds a capability
   the manifest's `scope` did not declare, the install is **rejected**, not
   warned about: an undeclared capability is exactly the case where an absent
   declaration _is_ the risk.
4. Materialise entities into the tenant library with provenance to
   `block@digest`. An install declares **`scope: tenant | workspace`** (the soft
   wall of Tenant & Identity §3), so a block private to client A does not appear
   to the team on client B.
5. **Quarantine through trust tiers.** A filler identity arriving in a block has
   no calibration with this tenant, so it starts at `gated` or `shadow` under the
   graduation policy (Role §5). No new moderation system is introduced.
6. Write the lockfile.

## 7. Upgrade and uninstall

An upgrade is a new digest, producing a **semantic diff per entity** — possible
because contents are typed — and then explicit migration. Running processes stand
still on their pinned version, following the same logic as Contract and Process
pinning.

**A way back is a condition, not a good intention.** An upgrade with migrations
runs only when the manifest declares `migrations[].down`, **or** declares
`irreversible_upgrade: true` — and in the latter case the engine **requires a
Gate and a copy taken beforehand**, exactly as North Star §8 requires of a major
migration. A downgrade runs the `down` steps in reverse and re-pins the old
digest, which always resolves because the lockfile kept it. A "revert" with no
prepared down path is a sentence, not a mechanism.

There is no auto-upgrade in any default configuration.

Uninstall keeps any entity a running instance still references, by pin, and
collects it when nothing does.

## 8. Public and private

The public instance is immutable with `yank` — hidden from resolution while
existing pins live forever, including for a paid block whose publisher has
disappeared.

Private distribution works on any OCI registry, with **scoped resolution** by
namespace, so a private block may depend on a public one. Air-gapped mirroring
uses standard commands; mirroring a paid namespace checks entitlement **at
mirror-pull time**, which keeps entitlement in the distribution layer and out of
the runtime.

A block is process knowledge, which is to say company IP. Private distribution is
not a nice-to-have.

## 9. Non-goals

- A Block carries no new runtime mechanism, and it carries no calibration:
  definitions are shared, learned data is not (invariant 4).
- No entitlement or DRM in the engine, and no auto-update.
- Contributing statistics or profiles back to the catalog is opt-in and passes a
  review round, consistent with Self-healing §5.

## 10. Decisions

| Question                  | Settled                                                                                                                                                                                                   |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| What a template is        | A Block curated for a vertical; the cascade's template level is the installed set, in the tenant's priority order                                                                                         |
| How many registries       | One protocol, one immutable public instance, N private mirrors. The Hub is the third domain, and both Platform and RPA speak to it directly through `resolve/pull/verify`                                 |
| Substrate                 | Git for development, OCI for distribution, a transparency log, an index; semver for people, digest for machines, a lockfile per tenant                                                                    |
| Trusting content          | Re-analyse tenant-side; a scope that disagrees with the analysis is rejected; quarantine through trust tiers; code is its own trust class                                                                 |
| Commerce                  | Entitlement only at distribution; no DRM; two licence tiers for content                                                                                                                                   |
| **An upgrade's way back** | `migrations[].down`, or `irreversible_upgrade: true` requiring a Gate and a copy — North Star §8's law mirrored down to the block layer. The lockfile keeps the old digest, so re-pinning always resolves |

## Litmus

1. When the manifest under-declares a capability the analysis finds, is the
   install rejected rather than warned about?
2. If the Hub disappears permanently, does every installed block — including a
   paid one — keep running, on the strength of the lockfile?
3. Is a code artifact from an unverified publisher rejected in every default
   configuration?
