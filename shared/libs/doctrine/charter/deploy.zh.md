# Ecoma — 部署与运维章程

这是一份章程，不是一份 spec：它不定义产品向租户承诺的机制。它定义的是运营方如何安装、
运行、备份、升级、回滚与关停一套安装——以及自托管者所得到的东西与运行托管服务的一方所
保留的东西之间，边界落在哪里。

## 边界：三个分区，不得混装

| 分区                | 什么住在这里                                                                                          | 是否发给自托管者？    |
| ------------------- | ----------------------------------------------------------------------------------------------------- | --------------------- |
| **部署**            | 自托管者**收到并运行**的东西：compose 文件、chart、service unit、安装器、迁移执行器、边缘路由配置模板 | 是                    |
| **运营方控制平面**  | 托管运营方的基础设施与控制平面：fleet、计费、配额运维、自动化 provisioning                            | 否——proprietary       |
| **开发工具**        | 开发本系统的人所用的工具：lint 规则、workspace 命令、仓库自动化                                       | 否——不是产品 artifact |
| **Enterprise 模块** | 面向**自托管**的企业级功能：单点登录、审计导出、深度保留、高级授权——且**不包含**多租户                | 是，需要一份 license  |

**单租户是部署形态的属性，不是引擎的技术限制。** 每一套自托管安装都只运行一个租户，因
为创建第二个租户的 workflow 只随运营方控制平面发布——**而不是**因为运行时校验了某个
entitlement，那正是 [Platform North Star](../north-star/platform.md) 明令禁止的。即便
cardinality 为一，引擎依旧在密钥树中保留租户层。因此本章程对多租户 provisioning 只字不
提；那是控制平面的事。

**这条边界的试金石只有一句话**：_部署分区中的每一个文件，都必须对一个正在自行安装的人
有用；只有**我们**需要的文件，就是放错了地方。_

朝一个方向错——内部基础设施漏进被发布的部分——等于把运维手册交给竞争对手。朝另一个方向
错——自托管者需要的东西却住在控制平面里——则让 fair-code 只在纸面上成立，因为自行安装的
人根本立不起这套系统。这就是边界要有**三个**分区而不是两个的原因：开发工具曾经是这两类
错误共同的藏身之处。

## 部署形态是一次规模声明，不是一个开关

两种形态，各自发布不同的一套：

| 形态            | 默认存储                                                       | 发布什么                                                  |
| --------------- | -------------------------------------------------------------- | --------------------------------------------------------- |
| **Small stack** | 嵌入式那一套，配一个基于文件的 vault                           | 二进制或镜像、service unit、配置模板、迁移执行器          |
| **Production**  | 一个同时承载日志、projection 与向量的数据库，配外部 vault 后端 | chart 或 compose 文件、密钥模板、迁移执行器、边缘路由模板 |

形态是**安装者的规模声明**，不是运行期翻动的开关。更换形态是一条有意为之的成长路径
——把日志重放进新的 port——且**永不**自动发生。一个运行期开关会把一项架构决策变成一次配
置事故。

本章程不定义存储 port 的 contract。那属于 [ADR-0002](../method/adr-ledger.md) 与
[Working Data](../spec/working-data.md)。

## 发布什么，以及各部件如何同行

服务端、无头 node 运行时、attended UI 层，以及挂载各公共界面的边缘路由配置模板。

**它们全部携带同一个 train 版本。** 安装器**拒绝**跨两个 train 的组合。在 attended 机
器上，同一台宿主机上有两个 artifact：UI 层在机内握手时校验 train，不一致就**拒绝运
行**——这种偏斜对系统里其他任何一次握手都是不可见的，因此它需要自己的检查。

缺少 train 版本、源 digest、provenance 或签名的 artifact 在**安装时被拒绝**。不存在"先
装上再说"的模式，因为正是那个模式让一个未签名的 artifact 进入了生产系统。

## 密钥与恢复

这是本章程最重的一节。底层规则属于 [Vault & Key](../spec/vault-key.md)——密钥材料永不
进入备份，根密钥与租户密钥的灾难恢复是强制的，且只有只向前的副本可以持有密钥材料。以下
是**流程**。

### 生成并确认根密钥

Provisioning **只发一次**根密钥，随后在让这套安装进入服务状态之前**要求一次校验和挑
战**。结果是一条日志条目。写下来的流程必须按形态**指名确切的存放位置**，而不是泛泛地建
议：

| 形态        | 根密钥的恢复路径，与数据备份路径分离                                                                              |
| ----------- | ----------------------------------------------------------------------------------------------------------------- |
| Small stack | 一份机外副本——一个密码管理器、一个密封信封、一个单独存放的 U 盘。流程至少指名一个具体选项，而不是让运营方自己去想 |
| Production  | 一个具备**只向前副本**的密钥管理服务或硬件模块，不提供时间点快照。资格在下文校验                                  |

"把密钥放在安全的地方"是一句建议。一个被指名的存放位置才是一道流程。

### 在一台空白机器上恢复

流程必须严格按此顺序运行：搭起一台新机器 → **从恢复路径载入根密钥** → 恢复数据 → 重放
→ 通过运行一次查询、读出**尚未**被粉碎的数据来验证。

**没有根密钥时，引擎直说无法恢复。** 它不会启动到一半，因为一套启动起来却什么都解不开
的安装，是一套看上去已恢复而实际上没有的安装。

### 一道闸：备份不得触碰密钥

一条 workspace 命令 `check-backup-key-isolation` 在持续集成中以及每次提交前运行：它扫
描部署分区中的每一个脚本、manifest 与 chart，只要有任何路径在任何部署形态下覆盖了根密
钥的位置，就**失败**。

_"不要备份密钥"是一句建议；一道红闸才是一个机制。_

### 哪些密钥存储合格

部署文档**显式声明**哪些后端有资格执行加密粉碎：`destroy` 必须**不可恢复**，且后端必须
不提供——或必须允许关闭——时间点快照或回退。带有强制恢复窗口的后端只有在该窗口可声明**且
粉碎命令只在窗口关闭之后才报告完成**时才算合格。

不合格的后端意味着引擎**拒绝承担加密粉碎这一角色**，而不是承诺一次它做不到的擦除。

## 备份与恢复

**什么进备份**：event log、artifact blob，以及可选的 projection —— projection 是可重建
的，因此备份它买到的是速度，永远不是正确性。

**什么永不进备份**：密钥材料，在每一层。

**保留期不得超过** [Release & Compatibility](../spec/release-compat.md) 所定义的支持窗
口，除非本章程声明了一条显式的恢复路径——把旧备份沿着迁移序列抬上来——并且该路径已经演
练过。在只支持两个 major 的同时保留五年备份，就是在守一个无法兑现的承诺。超出支持窗口
却没有声明恢复路径的保留设置，会**在启动时告警**，而不是悄无声息地通过。

**恢复演练是强制的，并且是一条日志条目。** 一套从未做过恢复测试的安装，握着的是一个
**假设**，不是一份保险。流程指明一个最小周期，并把每次演练的结果记入日志。

## 升级与回滚

四个阶段——并行安装、迁移、切换、保留——属于
[Release & Compatibility](../spec/release-compat.md)。本章程补上由人执行的那一部分。

**在触碰任何东西之前，preflight 是强制的**：确认所有 artifact 的 train 版本一致；确认
**本步骤中每一次 major 迁移都声明了 down-migration 或不可逆标志**；凡出现该标志之处，
在继续之前**要求一道 gate 和一份副本**；并确认最近一次备份已经演练过。

**两条不同的退路，各叫各的名字**：

| 在回滚窗口之内                                   | 在窗口之外                                                                                     |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| **回滚**：执行逆向迁移；先前的 artifact 仍在原处 | **不是回滚**——这是**恢复加重放**：从备份重建，接受自那份备份以来丢失的数据。风险不同，耗时不同 |

流程**禁止**对右栏使用"回滚"一词。运营方按下按钮，依据的是那个名字所携带的预期，因此把
两种不同的操作叫作同一个名字，就是在提前设计一次事故。

## 运维

- **健康与就绪**：只有当 vault 能打开、存储 port 有响应、且协议注册表加载完毕之后，就绪
  才转绿。提前转绿就是在对上游撒谎。
- **日志与指标**输出到安装者自己的输出或本地端点。**默认不 phone-home**——这是从天花板
  继承来的约束，不是一个配置选项。安装者要把它们转发到哪里是他们自己的事。
- **Lease 与心跳**：流程覆盖丢失心跳的 node，并且单独覆盖如何把它与**因超出版本偏斜窗口
  而拒绝领取**的 node 区分开。两者在 dashboard 上看起来一样，却需要相反的处置。
- **Fleet view**：哪个 node 跑哪个 train。正是这张表让偏斜规则可运维，而不只是理论。

## 关停一套安装

这与某个租户的生命周期不同：这里被关掉的是整整一套安装。

顺序是**强制的，不得调换**：(1) 通告，并关闭新的 trigger；(2) 让运行中的 task 完成或
escalate；(3) **先导出**，导成可读且完整的格式；(4) 在**另一台机器上**确认导出可读；
(5) **随后粉碎**；(6) 销毁基础设施。

把第 3 步与第 5 步对调，就是用一条命令永久丢失数据。第 4 步存在，是因为一份没人读过的
导出还不算存在——与上文的恢复演练是同一条论据。

## Non-goals

- **不是**托管运营方的基础设施，那部分不公开。
- **不是**存储 port 的 contract。
- **不是**构建、分支或持续集成。
- **不是**租户管理——本章程治理的是一套**安装**。
- **默认不做**遥测，无论叫什么名字。

## 试金石

1. 把部署分区交给一个陌生人：他们能否**不用运营方控制平面的任何一行**就把系统立起来？
2. 反过来：部署分区里是否有只有**我们**在用的文件——运维基础设施藏在了被发布的那一套里？
3. 往备份脚本里加一行、覆盖根密钥路径：持续集成会**变红**吗，还是文档里只有一句备注？
4. 一台空白机器加上从恢复路径取来的根密钥：跑完整套流程，是否以一条**可读的**未粉碎记
   录收尾？而在**没有**根密钥时，系统是否直说自己无法恢复，而不是启动到一半？
5. 在两个 major 的支持窗口下配置五年保留期且不声明恢复路径：系统会**在启动时告警**，还
   是保持沉默？
6. 读一读回滚流程：它有没有把"从备份恢复"叫作"回滚"？（必须的答案：没有。）
7. 一个丢失心跳的 node 与一个因版本偏斜而拒绝领取的 node：值班的人能否**从 fleet view
   分辨出来**，还是只能猜？
8. 跑一遍关停流程：是否存在任何一条通往粉碎步骤、却没有经过"在另一台机器上确认导出可
   读"这一步的路径？
9. 安装一套 attended UI 层与 node 运行时处于不同 train 的组合：安装器会**拒绝**，还是
   装上去之后再坏？
